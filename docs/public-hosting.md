# Hosting the portfolio tracker securely on the Surface

This is a **single-owner application**, not a multi-user financial service. Internet
reachability and permission to view/edit are separate: every page and API request
in public mode requires authentication. Broker API keys remain server-side and
must have read-only broker scopes. Editing this website never grants trading rights.

## Agreed topology: one hostname, three machines

```
solarpi.hopto.org:3000 -> router -> existing Raspberry Pi / Grafana
solarpi.hopto.org:4000 -> router -> existing Raspberry Pi / Grafana
https://solarpi.hopto.org:5000 -> router TCP 5000 -> Surface TCP 5000 (Caddy/TLS)
  -> 127.0.0.1:8000 (one Uvicorn worker, authenticated FastAPI + built React)
  -> /var/lib/stocks/portfolio.db (private SQLite)
```

The hostname remains **solarpi.hopto.org**; no additional subdomain is required.
The home router selects the internal machine by external port. The existing
Grafana forwards on **3000 and 4000 remain unchanged**. The proposed stocks rule
is external TCP 5000 to **192.168.7.205:5000** (reserve/recheck the Surface address).
Caddy and Uvicorn run on the Surface, not on either Pi. Do not forward to port 8000.

Both `STOCKS_ORIGIN` and `PORTFOLIO_PUBLIC_ORIGIN` must be exactly
`https://solarpi.hopto.org:5000`. The port is part of the browser's origin and is
required for authenticated edits. Caddy uses the explicit site port as its listener.

### Certificate issuance and renewal (decision still required)

Public HTTPS certificates cover hostnames, not ports, so a valid certificate for
`solarpi.hopto.org` works on 5000. However, ACME HTTP-01 validation reaches public
**port 80**, and TLS-ALPN-01 reaches public **port 443**, not port 5000.
Forwarding 5000 alone does not make automatic certificate issuance work.

The simplest option, if external port 80 is available, is an additional TCP 80
forward to the Surface's Caddy port 80 for automated certificate issuance/renewal.
Leave existing 3000/4000 mappings alone, and do not replace any existing 80/443 rule
without checking what uses it. If 80 cannot be forwarded, select a supported DNS-01
setup or an existing hostname certificate with a secure automated renewal/deployment
process; this requires separate configuration. Do not use self-signed certificates
or ignore browser warnings for public access. This decision is not yet implemented.

No HSTS is sent by default. HSTS affects an entire hostname, including HTTP Grafana
on other ports, so enabling it on `solarpi.hopto.org` can break those dashboards.
Consider HSTS only after using a dedicated hostname or moving every service on that
hostname to HTTPS. Never bypass certificate warnings or submit credentials over HTTP.

A WireGuard/Tailscale VPN is a smaller attack surface if only your own devices need
access. For browser access from arbitrary devices, use this HTTPS/authentication
boundary; an identity-aware proxy with MFA is the stronger follow-up for financial
information. This implementation does not provide MFA or multiple users.

## Security contract

- `PORTFOLIO_DEPLOYMENT_MODE=local` is loopback-only, not safe LAN/public mode.
- `public` refuses missing or invalid HTTPS origin, username or password hash.
- HTTP Basic authentication protects UI, assets and all API routes, including health.
  A browser prompts for credentials on first access; no password is bundled in JS.
- Passwords are stored only as salted scrypt hashes. Use a unique password of at
  least 16 characters, ideally generated by a password manager. No password in a URL,
  process command line, Git, chat, screenshot or log.
- Unsafe HTTP methods require `Origin` equal to `PORTFOLIO_PUBLIC_ORIGIN`, including
  the port if nonstandard. CLI API clients must send this header too; a stolen password
  is not made safe by CSRF protection. Cross-site browser requests are rejected.
- Host and HTTPS are checked using the ASGI request. Uvicorn trusts forwarded headers
  **only from 127.0.0.1**. Caddy overwrites those headers from the actual connection.
  Never use `--forwarded-allow-ips '*'` or expose port 8000.
- Authentication throttling is process-local. Use **one worker**; do not scale without
  a shared authentication/rate-limit design. Keep the Uvicorn concurrency limit.
- Requests are capped at 10 MiB, including multipart overhead. Both Caddy and the
  backend enforce the limit; chunked requests do not bypass it.
- No-store responses, frame denial, MIME sniffing prevention and a self-only script
  policy protect against accidental caching, clickjacking and third-party scripts.
  Inline styles remain enabled for charts. HSTS deliberately remains off (above).
- Error responses do not include raw SQL, paths or broker exception strings.

HTTP Basic has no reliable application logout button: browsers may retain it until
all related windows close. Use your own trusted device or a private browser window;
close it afterward. Password rotation invalidates the old credentials on service
restart. There is no self-service password recovery endpoint.

## Reviewable first-install script

On this Surface, use `deploy/install-surface.sh` as the normal `geoff` user:

```sh
cd ~/code/stocks
less deploy/install-surface.sh
bash deploy/install-surface.sh --check
bash deploy/install-surface.sh --install
```

Do **not** prefix the whole script with sudo. It first builds in a private staging
folder using system Python and hash-locked runtime dependencies, verifies the pinned
Caddy binary's SHA-512, and validates its configuration. It then shows the source
portfolio database, requires typing `INSTALL`, snapshots it with SQLite's backup API,
prompts for a website username/password, and invokes sudo for activation. Password
entry is masked; the administrator password and website password are separate.

`--check` is read-only. `--prepare-only` exercises downloads/builds without backups,
password prompts, sudo or service activation. Use `--database /path/to/portfolio.db`
to select a different existing source; the default is this repo's `portfolio.db`.
The source is never migrated: the service uses its own `/var/lib/stocks/portfolio.db`
copy. Subsequent website edits change that copy, not the original repo database.

This is **first-install only** and refuses existing deployment directories, service
files, a `stocks` account/group, an enabled packaged Caddy service, or occupied ports.
It creates `stocks.service` and a separate `stocks-proxy.service` with a dedicated
Caddy binary in the release (not the packaged `caddy.service` described by the manual
alternative below). The proxy uses HTTP-01 on port 80, HTTPS on 5000, and no admin API.
No router, firewall, power, Grafana or Hermes configuration is changed. If service/TLS
verification fails, it stops/disables only the new services and preserves the files
for diagnosis; rerunning will refuse that partial installation until reviewed.

The script keeps a private pre-migration snapshot under `/var/backups/stocks` and
retains its private staging folder. **Broker credentials are not copied.** If wanted,
add the read-only `PORTFOLIO_TRADING212_*` values using
`sudoedit /etc/stocks/production.env`, then `sudo systemctl restart stocks`.
Do not paste secrets into chat. Caddy's bundled version must be maintained deliberately;
this installer is not an automatic software updater or a backup scheduler.

At authoring time, Bash syntax, ShellCheck, ten installer guard tests, the read-only
preflight, real isolated build/Caddy verification and relocated system-Python imports
passed. The privileged activation phase was not run by the assistant; it requires
your local administrator authentication. Test public login from mobile data afterward.

## Prepare a release (manual alternative; not the live development checkout)

The repo includes `deploy/stocks.service`, `deploy/Caddyfile`, a Caddy systemd
drop-in, `requirements-production.txt` (hash-locked runtime dependencies), and
`scripts/deployment.py` (private config and SQLite backup). None auto-install services,
change firewall rules, migrate your existing database or open a router port.

Use a root-owned release under `/opt/stocks/releases/<release-id>` and a
`/opt/stocks/current` symlink. The service account `stocks` must have read/execute
access to code but **no write access to it**. It should not have access to your home,
SSH keys, Hermes credentials or the rest of the LAN through privileged accounts.
Build in a staging directory; only switch the symlink after verification.

1. Install a maintained system Python (3.11+) and packaged Caddy from its official
   repository. Use a dedicated system user/group named `stocks` with no login shell.
   Create `/var/lib/stocks` owned by that user with mode 0700, and `/etc/stocks` root
   owned with mode 0700. Do not reuse Geoff's user account for the public process.
2. Create the release virtualenv using **system Python outside `/home`**, then install:
   ```sh
   uv pip install --python /opt/stocks/current/.venv/bin/python \
     --require-hashes -r /opt/stocks/current/requirements-production.txt
   ```
   `ProtectHome=true` in the unit means a venv whose Python points into
   `/home/geoff/.local/share/uv` will not work. Recreate that venv with system Python;
   do not copy the development `.venv` or disable ProtectHome as a workaround.
3. Build the React frontend on the staging release:
   ```sh
   npm --prefix frontend ci --ignore-scripts
   npm --prefix frontend run typecheck
   npm --prefix frontend run build
   ```
   This produces `frontend/dist`. Never run Vite dev/preview publicly. The production
   API serves the built files at the same origin, so reads/uploads/edits need no
   wildcard CORS configuration. Keep node_modules out of the deployed release.
4. Before moving a real portfolio, create a **verified private SQLite backup** with
   the backup helper below. Transfer it securely outside Git and restore it to
   `/var/lib/stocks/portfolio.db`, owned by `stocks`, mode 0600. Do not substitute an
   empty database unless starting a new portfolio is intentional. Broker credentials
   and imported data on the gaming machine are not automatically copied to the Surface.
5. In an interactive terminal, create a new private configuration file:
   ```sh
   /opt/stocks/current/.venv/bin/python /opt/stocks/current/scripts/deployment.py configure \
     --output /path/to/private/production.env \
     --origin https://solarpi.hopto.org:5000 \
     --username YOUR-LOGIN \
     --database /var/lib/stocks/portfolio.db \
     --dist /opt/stocks/current/frontend/dist
   ```
   Password entry is masked. The helper refuses to overwrite an existing file, invalid
   origin or short password. Install the resulting file as `/etc/stocks/production.env`,
   root-owned, mode 0600. Keep a password-manager copy of your actual password. If broker
   sync is wanted, add the documented `PORTFOLIO_TRADING212_*` credentials privately to
   that file, not this repository. Do not copy a development `.env` into a served release.
6. Put the **same exact HTTPS origin** in `/etc/stocks/caddy.env`:
   ```dotenv
   STOCKS_ORIGIN=https://solarpi.hopto.org:5000
   ```
   Use the bundled Caddy configuration only for a dedicated Caddy instance. Install
   the provided `caddy-stocks.conf` drop-in under
   `/etc/systemd/system/caddy.service.d/stocks.conf` so Caddy receives this variable.
   Validate its configuration using `caddy validate` with that variable supplied.
7. Install/review `stocks.service`. It binds only loopback, runs unprivileged, denies
   writes outside its state directory, and limits memory/concurrency. Check its
   effective configuration and filesystem permissions before starting it.

The application currently runs Alembic migrations during startup. They must use the
same explicitly configured database as application sessions, not alembic.ini's old
development path. Set `PORTFOLIO_DATABASE_URL` before importing `app.main`; the
`create_app(config)` factory rejects conflicting database settings rather than
silently using the process-global database. Direct `alembic upgrade` with the old
INI is not the supported deployment path. Make a verified snapshot **before any version upgrade/restart with
new migrations**. Start only one worker; do not run simultaneous migration processes.
A failed startup should be investigated, not repeatedly restarted against real data.

## Go-live gate (separate operator action)

Before changing external access, verify all of the following:

- Back up the current database and any existing proxy/service/firewall configuration.
- Start the app and test through local Caddy with the intended HTTPS origin, first
  using disposable data. Confirm unauthenticated reads **and writes** are denied,
  valid credentials work, and absent/wrong Origin blocks updates.
- Confirm a real frontend deep link loads (for example `/portfolio?tab=holdings`),
  then exercise one reversible edit or an import on a disposable database.
- Confirm port 8000 is reachable only via loopback, including IPv6. Router forwards
  must never target 8000, 5173, 3000 (Hermes bridge) or Caddy's admin API 2019.
- Reserve the Surface's LAN address in DHCP. It was observed as **192.168.7.205**
  during preparation; recheck it rather than treating that as a permanent address.
- Confirm the DDNS updater stays active on an always-on machine. Confirm no stale
  AAAA record sends IPv6 traffic elsewhere. Check IPv6 firewall exposure separately.
- Confirm ISP/router allow inbound traffic (CGNAT may prevent forwarding).
- The user configures router forwarding: TCP 5000 -> Surface TCP 5000. Keep the
  Grafana 3000/4000 forwards unchanged. Complete the certificate/renewal decision
  above before public login; an optional TCP 80 forward is for ACME and redirect,
  not password entry. No external 443 forwarding is required if HTTP-01 is used.
- Allow only those intended public ports through the host firewall; don't blindly
  enable/reset a firewall or disrupt SSH/Grafana. Keep 8000 loopback regardless.
- Test from a phone with **Wi-Fi turned off**, with a valid certificate and without
  skipping TLS validation. Verify login, reads, a reversible update and denied access
  in a fresh unauthenticated browser. Test all existing Grafana URLs unchanged.
- Verify startup after reboot and that the Surface will not sleep when plugged in or
  its cover closes. Review the power settings deliberately; don't change them blindly.

External reachability cannot be proved by a local curl or a hairpin-NAT request. The
repo being prepared does not mean port forwarding, a public certificate, login setup,
real-data migration or reboot reliability has been completed.

## Backups, updates and rollback

Use SQLite's snapshot API, not `cp` of a running WAL-mode database:

```sh
.venv/bin/python scripts/deployment.py backup \
  --source /path/to/source/portfolio.db \
  --output /private/backups/portfolio-UNIQUE-ID.db
```

The helper requires an existing source, refuses to overwrite/follow an existing
output symlink, writes mode 0600, and requires `PRAGMA integrity_check == ok`. The
parent backup directory must already exist and be private. Keep encrypted off-machine
copies and a retention policy; **no scheduled backup is installed automatically**.
Rehearse restoring a copy on a disposable instance, checking content as well as
integrity before relying on the backup. Tests of synthetic files do not prove your
actual portfolio backup is complete.

For an upgrade: preserve the old code release and private environment; snapshot the
DB; build/install/test a new release in isolation; stop stocks; switch release;
restart; verify authenticated read/write and logs. Do not edit a running `--reload`
checkout. Review dependency audits regularly; a zero finding is not a security proof.

If a migration or upgrade fails, stop stocks, preserve the failed DB plus WAL/SHM
sidecars for diagnosis, restore the verified pre-upgrade snapshot into a new file,
restore old code/config, then restart and verify. Do not merely roll back code against
a changed schema, overwrite a running SQLite file, or delete evidence. Any writes
since the snapshot would be lost and need explicit acceptance. To remove public
access quickly, disable only the stocks proxy/forward; keep Grafana untouched.

## Known limits

- Single-user password auth, not MFA/RBAC/auditable per-user change history.
- Auth throttling, byte/concurrency/time/memory limits reduce abuse but do not prevent
  distributed denial of service. Spreadsheet parsing and expensive portfolio/quote
  calculations remain resource-heavy. Only import files you trust.
- A password compromise gives the attacker the same local portfolio editing powers
  as the owner. Broker read-only API keys restrict broker impact, not data disclosure.
- Safe error messages intentionally provide less import diagnostic detail.
- The Surface, router, TLS renewal, DNS and backup storage all need ongoing patching
  and monitoring; this is not a managed hosting service.
